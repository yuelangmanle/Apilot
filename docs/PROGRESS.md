## 三、核心设计（供后续维护者参考）

- **模型商店 / 广场**：列表阶段只用名字做启发式（要快），**真实文件与体积在详情页按需解析**；
  能力标签优先用"文件事实"（仓库里有 `mmproj*.gguf` 才算能看图）。
- **视觉投影（mmproj）默认按模型专用处理**：只接受下载完成时记录的明确配对；同一仓库的量化变体只有在显式共享组下才复用，不能跨仓库猜测或自动套用。App 内仍提供手动配对入口。
- **对话上下文**：分层管理——70% 水位零成本折叠（截短旧工具输出）→ 85%（可调）做
  **增量摘要**（与已有摘要合并去重），用户诉求原样保留；顶部显示占用百分比。
- **AI 插件**：统一 `@@TOOL` 协议（兼容 `@@工具名 {}` 与裸 JSON），本地与云端共用；
  每个分类独立开关并持久化；工具文档"一行式"注入（避免拖慢预填充）。
- **网关**：云端配置转发 或 本机模型离线推理；Android 前台服务保活。
- **后端调试闭环**：网关提供只读 `/v1/health` 与 `/v1/diagnostics`，可从 ADB、模拟器或第三方脚本检查模型、投影、下载和工具状态，不依赖截图操作。
- **引擎生命周期**：同一 native 引擎的加载与生成都串行化，聊天页复用已注册实例；页面退出不再误释放仍被工具/诊断使用的引擎。

# 附：本地推理提速的深度剖析（从根本出发）

> 结论先行：**手机端推理速度由"内存带宽"决定，不由"代码写得快不快"决定。**
> 想从根本提速，只有五条路，按性价比排序：

## 1. 让每次请求只算"新增的 token"（已启用 + 已修复前缀断点）
多轮对话里，前面所有内容的结果（KV cache）本可以复用，只算新输入。
llamadart 的 `GenerationParams.defaultReusePromptPrefix = true` 已默认开启，
**但前提是提示词前缀稳定**。修复了两处前缀断点：
1. v2.7.5 前每轮把"记忆检索结果"拼进 system 提示词 → 改为**每会话只检索一次**（v2.7.7）；
2. v2.7.8 发现工具模式只发"最近 6 条"历史的**滑动窗口**——窗口一滑，
   全部前缀错位，KV 复用完全失效。改为**传完整历史**。
预期收益：长对话第 N 轮的 prefill 从 O(N) 降到 O(1)，体感"越聊越跟手"。

## 2. 让模型少算"每个 token"（GPU 卸载，已修）
逐 token 生成受**内存带宽**限制，GPU（Vulkan / Metal）的带宽远高于移动 CPU：
社区实测 Qwen3-0.6B 18→28 tok/s、Llama-3.2-3B 8→14 tok/s（约 1.5–2×）。
移动端 GPU 驱动差异很大，均衡档默认使用 CPU 兼容路径；只有“GPU 加速（实验）”或高级项显式选择时才请求 Vulkan，
并保留加载失败自动回退 CPU。注意：安卓上 GPU 层数 > 0 时 flash-attention 可能被后端自动调整。

## 3. 让硬件算得更快（已核实：预编译库已带 i8mm/dotprod）
手机 SoC 普遍支持 `i8mm` / `dotprod` 指令，对 Q4/Q8 量化推理有 30–50% 提升。
**binary 级核实结论（v2.7.8）**：llamadart 的 android-arm64 bundle 内含
4 个按 ISA 分级的 CPU 变体（armv8.0_1 / armv8.2_2 / armv8.6_1 / armv9.2_1），
运行期按 CPU 能力自动分发；`armv8.6` 变体内 `i8mm` 符号 144 处、
`ggml_gemm_*_8x8_q8_0` 微内核在位。**无需自建 native bundle**。
KleidiAI 未打包（可向上游提 issue，属锦上添花）。

## 4. 线程数与 batch 调优（已暴露 UI）
- **生成**受内存带宽限制：大核 2–4 线程通常最优，线程过多反而因 cache 竞争变慢
  → 默认交自动，省电档压到 2。
- **预填充**受算力限制：线程越多越快 → `numberOfThreadsBatch` 取 `max(线程,4)`。
- 均衡档的 `batch` 收敛为 128；性能档为 256，省内存档为 64，避免移动端一次性预填充过大造成卡顿。
- 内存 ≤4GB 的设备建议 2048 上下文 + Q4_K_M 或更小量化。

## 5. 投机解码（已落地：n-gram 自推测）
两条路线，我们选了**零额外内存**的那条：
- ~~小模型草稿（draft-model）~~：要同族 0.5B 级小模型、显存放两个，条件苛刻；
- **n-gram 自推测（已实现，v2.7.8）**：用刚生成文本自身的 n-gram 模式做草稿，
  大模型只做校验。不需要第二个模型、零额外内存，**代码/HTML/重复格式场景
  预期 1.5–2×**，闲聊类收益小。走 `SpeculativeDecodingConfig.ngramSimple()`，
  同时在 ModelParams 里预留 `speculativeRollbackTokenMax=64`（官方要求
  snapshot ≥ 有效草稿长度 48）。原生库不支持时**自动降级重试**，绝不影响可用性。
  开关位置：对话页 → 参数 → 高级性能选项。

## 不建议做的事（避免走弯路）
- **不要盲目调大上下文**：KV 内存线性增长，超过物理内存会触发换页，反而骤慢。
- **不要默认开 KV q8_0**：它省内存，但部分机型/后端上更慢（我们已改为默认关）。
- **不要指望"多开线程"通吃**：生成阶段线程过多会变慢，"越多越快"只适用于预填充。
- **不要在提示词里塞无关内容**：每多一个 token，每一轮都要重算（除非前缀稳定）。

## 当前默认参数（均衡档）
`CPU · 4 线程 · FlashAttention 开 · KV f16 · batch 128 · 上下文 4096`
——GPU 卸载、KV q8_0、投机解码和线程/GPU 层数覆盖都在「参数 → 高级性能选项」中，修改后会重载模型。
